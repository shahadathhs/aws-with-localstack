## Declare the result, not the steps

Every lab so far was **imperative**: a list of commands, run in order. Run the script twice and `create-bucket` fails the second time, or worse, creates a duplicate. Someone has to remember what has already been done.

Terraform is **declarative**. You write the **desired state**, files that say "a bucket named `tf-notes` exists, and so does this queue". Terraform compares that with what is actually there and works out the steps itself. The pieces:

- **Provider**: a plugin that knows one platform's API. The `aws` provider turns your description into AWS API calls.
- **Resource**: one thing that should exist, such as `aws_s3_bucket`. It has a type, a local name (`notes`), and arguments.
- **State**: a file where Terraform records which real objects it created for which resources. It is how Terraform knows that `aws_s3_bucket.notes` *is* the bucket `tf-notes`.

And three commands you will use constantly:

| Command | What it does |
| --- | --- |
| `init` | downloads the providers the configuration needs |
| `plan` | compares the files, the state and reality, and prints what it *would* do; changes nothing |
| `apply` | does it |

## Terraform without installing it

This course runs Terraform from the official Docker image through Compose, so there is nothing to install. `make tf CMD="..."` runs `terraform ...` against LocalStack, in the folder `labs/terraform/`. Terraform reaches LocalStack by its Compose name, `http://localstack:4566`. The first run pulls the image and the AWS provider, so it needs a network connection and takes a minute.

<Note title="The provider block is the LocalStack part">
  The `endpoints` and the `skip_...` lines in the provider tell it to talk to LocalStack and skip checks that need a real account. Against real AWS you delete them, and the rest of the file is the same.
</Note>

## First configuration

<Lab title="three resources from one file" time="~8 min">
  <Predict>
    A file declares a bucket, a queue and a DynamoDB table, none of which exist. What does `plan` report? After `apply`, what does a second `plan` report?

    <Answer>
      The first plan says **3 to add, 0 to change, 0 to destroy**. After `apply`, the second says **No changes**: the real world already matches the files, so there is nothing to do. That is what makes `apply` safe to repeat.
    </Answer>
  </Predict>
  <Run>
Run these from the repository root, with LocalStack up (`make up`). First write the configuration:

```sh
cat > labs/terraform/main.tf <<'EOF'
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region                      = "eu-west-1"
  skip_credentials_validation = true
  skip_metadata_api_check     = true
  skip_requesting_account_id  = true
  s3_use_path_style           = true

  endpoints {
    s3       = "http://localstack:4566"
    sqs      = "http://localstack:4566"
    dynamodb = "http://localstack:4566"
  }
}

resource "aws_s3_bucket" "notes" {
  bucket = "tf-notes"
}

resource "aws_sqs_queue" "jobs" {
  name                       = "tf-jobs"
  visibility_timeout_seconds = 30
}

resource "aws_dynamodb_table" "tasks" {
  name         = "tf-tasks"
  billing_mode = "PAY_PER_REQUEST"
  hash_key     = "id"

  attribute {
    name = "id"
    type = "S"
  }
}
EOF
```

Download the provider, then ask what Terraform would do:

```sh
make tf CMD="init -no-color"
make tf CMD="plan -no-color"
```
<Output>
```text
# trimmed to the lines that matter
- Installed hashicorp/aws v5.100.0 (signed by HashiCorp)
Terraform has been successfully initialized!
...
Plan: 3 to add, 0 to change, 0 to destroy.
```
</Output>

`-no-color` only keeps this page readable; leave it out in your own terminal. Now make it so, and check with the AWS CLI that the objects exist:

```sh
make tf CMD="apply -auto-approve -no-color"

export AWS_PROFILE=localstack
aws s3 ls | grep tf-
aws sqs list-queues --query 'QueueUrls' --output text
aws dynamodb list-tables --query TableNames --output text
```
<Output>
```text
# trimmed; the queue takes about half a minute to create here
Apply complete! Resources: 3 added, 0 changed, 0 destroyed.
2026-10-29 11:58:20 tf-notes
http://sqs.eu-west-1.localhost.localstack.cloud:4566/000000000000/tf-jobs
tf-tasks
```
</Output>

Run `plan` again:

```sh
make tf CMD="plan -no-color"
```
<Output>
```text
No changes. Your infrastructure matches the configuration.
```
</Output>
  </Run>
  <Verify>
    - The first plan ends `Plan: 3 to add, 0 to change, 0 to destroy.`
    - The AWS CLI shows `tf-notes`, `tf-jobs` and `tf-tasks`
    - The second plan says `No changes`
  </Verify>
</Lab>

<Lab title="edit the file, not the queue" time="~4 min" collapsed>
  <Predict>
    You change `visibility_timeout_seconds` from 30 to 60 in the file and run `plan`. Will Terraform delete and recreate the queue, or update it?

    <Answer>
      **Update in place**: `Plan: 0 to add, 1 to change, 0 to destroy`, with a line `visibility_timeout_seconds = 30 -> 60`. Terraform knows this argument can be changed on a live queue. Some arguments cannot, and for those it replaces the resource.
    </Answer>
  </Predict>
  <Run>
```sh
sed -i.bak 's/visibility_timeout_seconds = 30/visibility_timeout_seconds = 60/' labs/terraform/main.tf
make tf CMD="plan -no-color"
make tf CMD="apply -auto-approve -no-color"
```
<Output>
```text
# trimmed
~ visibility_timeout_seconds        = 30 -> 60
Plan: 0 to add, 1 to change, 0 to destroy.
Apply complete! Resources: 0 added, 1 changed, 0 destroyed.
```
</Output>

Put it back to 30 so the next lessons start from the same file:

```sh
sed -i.bak 's/visibility_timeout_seconds = 60/visibility_timeout_seconds = 30/' labs/terraform/main.tf
make tf CMD="apply -auto-approve -no-color"
```
  </Run>
  <Verify>
    - The plan shows one change, an in-place update, not a destroy
    - Before you put it back, `aws sqs get-queue-attributes` on `tf-jobs` reports a `VisibilityTimeout` of 60
  </Verify>
</Lab>

## What changes on real AWS

<RealAws title="Remove the LocalStack lines">
  Delete the `endpoints` block and the `skip_...` and `s3_use_path_style` lines, and give Terraform real credentials the usual way (a profile or environment variables). The resources are unchanged. Bucket names must then be globally unique across all of AWS, so `tf-notes` will probably already be taken.
</RealAws>

<RealAws cost title="Apply creates real, billed things">
  On real AWS, `apply` creates resources that cost money while they exist. Read the plan every time, and `destroy` what you do not need.
</RealAws>

<Note title="plan is the safety net">
  A plan that says "1 to destroy" when you expected "1 to change" is the moment to stop. Teams often require someone to read the plan before an apply.
</Note>

<Recap>

- Terraform is declarative: you describe the end state, and it computes the steps.
- `init` fetches providers, `plan` shows the difference without changing anything, `apply` makes it so.
- Because the state records what exists, running `apply` twice does nothing the second time.

</Recap>
