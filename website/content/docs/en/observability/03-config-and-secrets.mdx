## Config is not code

Where a value lives decides who can read it and how quickly it can change.

- **In the code** (or the build): everyone with the repository can read it, and changing it means a deploy. Never put a secret here.
- **In an environment variable**: set on the function, so anyone who can *describe* the function can read it. It is visible in the console and in `get-function-configuration`, and it is easy to copy into logs.
- **In a secrets store**: read at runtime through an API call that is authorised and audited, and changed without redeploying.

AWS gives you two stores:

| Store | For | Notes |
| --- | --- | --- |
| **Secrets Manager** | passwords, API keys, tokens | versioned, can be rotated, billed per secret |
| **Systems Manager Parameter Store** | settings and light secrets | hierarchical names like `/shop/log-level`; `String` or encrypted `SecureString` |

## A secret has versions

Updating a secret does not overwrite it. It adds a **version** and moves labels called **staging labels**: `AWSCURRENT` is the version your code gets by default, and the one before it becomes `AWSPREVIOUS`, so you can roll back.

<Lab title="update a secret and read the old one" time="~5 min">
  <Predict>
    You create a secret `hunter2`, then store the new value `correct-horse`. What does a plain read return, which labels exist, and how do you read the old value?

    <Answer>
      A plain read returns **`correct-horse`**, the `AWSCURRENT` version. Two versions exist, labelled `AWSCURRENT` and `AWSPREVIOUS`. Ask for `--version-stage AWSPREVIOUS` to get `hunter2` back.
    </Answer>
  </Predict>
  <Run>
```sh
export AWS_PROFILE=localstack

aws secretsmanager create-secret --name shop/db-password --secret-string 'hunter2'
aws secretsmanager put-secret-value --secret-id shop/db-password --secret-string 'correct-horse'

echo "current:"
aws secretsmanager get-secret-value --secret-id shop/db-password \
  --query SecretString --output text
echo "labels:"
aws secretsmanager list-secret-version-ids --secret-id shop/db-password \
  --query 'Versions[].VersionStages' --output text
echo "previous:"
aws secretsmanager get-secret-value --secret-id shop/db-password \
  --version-stage AWSPREVIOUS --query SecretString --output text
```
<Output>
```text
current:
correct-horse
labels:
AWSCURRENT
AWSPREVIOUS
previous:
hunter2
```
</Output>
  </Run>
  <Verify>
    - The default read is `correct-horse`
    - Two versions exist, one `AWSCURRENT` and one `AWSPREVIOUS` (the order of the two lines may differ)
    - The previous value is still retrievable
  </Verify>
</Lab>

<Lab title="deleting is a countdown" time="~3 min" collapsed>
  <Predict>
    You delete the secret with a 7-day recovery window and read it straight away. Can you read it, and can you undo the delete?

    <Answer>
      **No** to the read: it fails with `InvalidRequestException` because the secret is marked for deletion. **Yes** to the undo: `restore-secret` cancels the deletion during the window.
    </Answer>
  </Predict>
  <Run>
```sh
aws secretsmanager delete-secret --secret-id shop/db-password --recovery-window-in-days 7
aws secretsmanager get-secret-value --secret-id shop/db-password
aws secretsmanager restore-secret --secret-id shop/db-password
```
<Output>
```text
# the delete response (ARN, deletion date) is left out
aws: [ERROR]: An error occurred (InvalidRequestException) when calling the GetSecretValue operation: You can't perform this operation on the secret because it was marked for deletion.
{
    "ARN": "...",
    "Name": "shop/db-password"
}
```
</Output>
  </Run>
  <Verify>
    - The read fails while the delete is pending, and works again after the restore
  </Verify>
</Lab>

## Read the secret at runtime

The handler below reads the secret on the first call and keeps it in a global variable, the cache you met in the [execution model lesson](/en/lambda/01-execution-model/). Later calls on the same warm instance skip the network call. It also reports whether the password appears in the function's environment.

<Lab title="a function that fetches its own secret" time="~6 min">
  <Predict>
    You invoke the function twice. Then you put the same password in an environment variable and invoke again. What does `fetched` say on each call, and who can now see the password without calling Secrets Manager?

    <Answer>
      `fetched` is **true** on the first call and **false** on the second: a warm instance reuses the cached value. After the function is reconfigured it is **true** again, because a configuration change starts a fresh instance, and `in_env` becomes **true**. Anyone who can describe the function can now read the password with `get-function-configuration`.
    </Answer>
  </Predict>
  <Run>
```sh
mkdir -p /tmp/cfg && cd /tmp/cfg

cat > sec.py <<'PY'
import os

import boto3

client = boto3.client("secretsmanager")
cached = None


def handler(event, context):
    global cached
    fetched = cached is None
    if fetched:
        cached = client.get_secret_value(SecretId="shop/db-password")["SecretString"]
    return {"fetched": fetched, "length": len(cached), "in_env": "correct-horse" in str(dict(os.environ))}
PY
zip sec.zip sec.py
aws iam create-role --role-name lambda-role --assume-role-policy-document '{
  "Version": "2012-10-17",
  "Statement": [{ "Effect": "Allow", "Principal": { "Service": "lambda.amazonaws.com" }, "Action": "sts:AssumeRole" }]
}'
aws lambda create-function --function-name readsec --runtime python3.12 \
  --handler sec.handler --zip-file fileb://sec.zip \
  --role arn:aws:iam::000000000000:role/lambda-role
aws lambda wait function-active-v2 --function-name readsec

for i in 1 2; do
  aws lambda invoke --function-name readsec --cli-binary-format raw-in-base64-out out.json >/dev/null
  cat out.json; echo
done
```

Now do what you should *not* do: put the password in an environment variable, and see who can read it.

```sh
aws lambda update-function-configuration --function-name readsec \
  --environment 'Variables={DB_PASSWORD=correct-horse}'
aws lambda wait function-updated-v2 --function-name readsec

aws lambda invoke --function-name readsec --cli-binary-format raw-in-base64-out out.json >/dev/null
cat out.json; echo
aws lambda get-function-configuration --function-name readsec --query Environment.Variables
```
<Output>
```text
{"fetched": true, "length": 13, "in_env": false}
{"fetched": false, "length": 13, "in_env": false}
{"fetched": true, "length": 13, "in_env": true}
{
    "DB_PASSWORD": "correct-horse"
}
```
</Output>
  </Run>
  <Verify>
    - `fetched` is `true`, then `false`: the second call used the cache
    - After the environment variable, `in_env` is `true`, and `get-function-configuration` prints the password in plain text
  </Verify>
</Lab>

<Lab title="settings in Parameter Store" time="~3 min" collapsed>
  <Predict>
    You store `/shop/log-level` as a `String` and `/shop/api-key` as a `SecureString`. How do you list everything under `/shop`, and what must you add to read the encrypted value in the clear?

    <Answer>
      `get-parameters-by-path --path /shop` lists both names. Reading a `SecureString` needs `--with-decryption`, otherwise you get the encrypted form.
    </Answer>
  </Predict>
  <Run>
```sh
aws ssm put-parameter --name /shop/log-level --value info --type String
aws ssm put-parameter --name /shop/api-key --value k123 --type SecureString

aws ssm get-parameters-by-path --path /shop --query 'Parameters[].Name' --output text
aws ssm get-parameter --name /shop/api-key --with-decryption --query Parameter.Value --output text
```
<Output>
```text
/shop/log-level	/shop/api-key
k123
```
</Output>
  </Run>
  <Verify>
    - Both names are listed, and the decrypted value is `k123`
  </Verify>
</Lab>

## What changes on real AWS

<RealAws title="The function needs permission to read the secret">
  On real AWS the execution role must allow `secretsmanager:GetSecretValue` on that secret's ARN, and the key that encrypts it. LocalStack does not enforce this, so the lab runs without it. Grant the one secret, not `*`.
</RealAws>

<RealAws cost title="Secrets are billed, calls are billed">
  Secrets Manager charges per secret per month and per 10,000 API calls, so reading the secret on every invocation costs money and time. Cache it in a global, as above, and refresh on a schedule or when a read fails. Parameter Store standard parameters are free.
</RealAws>

<Note title="Rotation">
  Real Secrets Manager can rotate a secret on a schedule by running a Lambda function that changes the password in the database and in the secret together. The staging labels you saw are how a rotation swaps the new value in safely.
</Note>

<Recap>

- A secret in code or an environment variable is visible to everyone who can read the repository or describe the function.
- Secrets Manager keeps versions with labels: `AWSCURRENT` by default, `AWSPREVIOUS` for roll-back.
- Read a secret at runtime and cache it in a global; parameters hold ordinary settings, and `SecureString` encrypts them.

</Recap>
