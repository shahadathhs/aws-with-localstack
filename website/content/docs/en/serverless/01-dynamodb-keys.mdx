## One question, answered fast

DynamoDB is not a database you filter after the fact. Every item lives at a place decided by its **partition key**: the key is hashed, and the hash picks which storage partition holds the item. A request that names the key goes straight to that place. A request that does not has to visit all of them.

- **Partition key**: required, picks the partition. `userId` in the table below.
- **Sort key**: optional. Items with the same partition key are stored together, ordered by sort key, so you can fetch a range of them. `taskId` below.
- Together they form the item's **primary key**, and it must be unique.

Two operations read many items, and they could not be more different:

| Operation | Needs | Reads |
| --- | --- | --- |
| **Query** | the partition key, and optionally a condition on the sort key | only the items under that key |
| **Scan** | nothing | every item in the table, and *then* applies your filter |

A filter on a scan does not make it cheaper: you still pay to read what you throw away. That is the paradigm shift from a relational or document database: you decide your queries first, then choose keys that make them fast. There are no joins and no ad-hoc queries.

<Note title="Billing is per read and write">
  On-demand tables charge per request unit, and provisioned tables sell throughput (RCU and WCU) per second. Either way, the cost follows how many items you touch. LocalStack does not meter this faithfully, so the lab below compares **how many items were read**, which is the thing the bill follows.
</Note>

## Keys in practice

<Lab title="query by key, scan, and a wrong question" time="~6 min">
  <Predict>
    A table has three tasks for `ana` (two open, one done) and one for `bo`. You scan with the filter `status = open`. How many items does the response *return*, and how many did DynamoDB *scan*?

    <Answer>
      It returns **3** (the open ones) but scans **4**, every item. The filter runs after the read. A query for `userId = ana` would scan only her 3.
    </Answer>
  </Predict>
  <Run>
```sh
export AWS_PROFILE=localstack

aws dynamodb create-table --table-name tasks \
  --attribute-definitions AttributeName=userId,AttributeType=S AttributeName=taskId,AttributeType=S \
  --key-schema AttributeName=userId,KeyType=HASH AttributeName=taskId,KeyType=RANGE \
  --billing-mode PAY_PER_REQUEST

aws dynamodb put-item --table-name tasks --item '{"userId":{"S":"ana"},"taskId":{"S":"t1"},"title":{"S":"task 1"},"status":{"S":"open"}}'
aws dynamodb put-item --table-name tasks --item '{"userId":{"S":"ana"},"taskId":{"S":"t2"},"title":{"S":"task 2"},"status":{"S":"done"}}'
aws dynamodb put-item --table-name tasks --item '{"userId":{"S":"ana"},"taskId":{"S":"t3"},"title":{"S":"task 3"},"status":{"S":"open"}}'
aws dynamodb put-item --table-name tasks --item '{"userId":{"S":"bo"},"taskId":{"S":"t1"},"title":{"S":"bo task"},"status":{"S":"open"}}'
```

Only the key attributes are declared up front; every other attribute (`title`, `status`) is free-form per item. Now ask for ana's tasks by key, then ask the same table a question the key cannot answer:

```sh
echo "query by key:"
aws dynamodb query --table-name tasks --key-condition-expression 'userId = :u' \
  --expression-attribute-values '{":u":{"S":"ana"}}' \
  --query '[Count,ScannedCount]' --output text

echo "scan with a filter:"
aws dynamodb scan --table-name tasks --filter-expression '#s = :o' \
  --expression-attribute-names '{"#s":"status"}' \
  --expression-attribute-values '{":o":{"S":"open"}}' \
  --query '[Count,ScannedCount]' --output text

echo "query on a non-key attribute:"
aws dynamodb query --table-name tasks --key-condition-expression '#s = :o' \
  --expression-attribute-names '{"#s":"status"}' \
  --expression-attribute-values '{":o":{"S":"open"}}'
```
<Output>
```text
query by key:
3	3
scan with a filter:
3	4
query on a non-key attribute:

aws: [ERROR]: An error occurred (ValidationException) when calling the Query operation: Query condition missed key schema element: userId
```
</Output>
  </Run>
  <Verify>
    - The query returns 3 and scanned 3: it touched only ana's items
    - The scan returns 3 but scanned 4: it read bo's item too, just to discard it
    - The third command is **refused**: a query must name the partition key
  </Verify>
</Lab>

## A second question needs a second key

"All open tasks, whoever owns them" is a different question, and `status` is not in the primary key. The answer is a **global secondary index** (GSI): a copy of the table, maintained for you, organised under a different key. You query the index exactly like a table.

<Lab title="add an index and ask again" time="~4 min">
  <Predict>
    You add an index with partition key `status`. You query it for `status = open`. How many items are scanned, and do they come from one user or several?

    <Answer>
      **3 scanned and 3 returned**, from both users: the index is organised by status, so the open items sit together regardless of owner.
    </Answer>
  </Predict>
  <Run>
```sh
aws dynamodb update-table --table-name tasks \
  --attribute-definitions AttributeName=status,AttributeType=S AttributeName=taskId,AttributeType=S \
  --global-secondary-index-updates '[{"Create":{"IndexName":"by-status",
    "KeySchema":[{"AttributeName":"status","KeyType":"HASH"},{"AttributeName":"taskId","KeyType":"RANGE"}],
    "Projection":{"ProjectionType":"ALL"}}}]'
sleep 3

aws dynamodb query --table-name tasks --index-name by-status \
  --key-condition-expression '#s = :o' \
  --expression-attribute-names '{"#s":"status"}' \
  --expression-attribute-values '{":o":{"S":"open"}}' \
  --query '[Count,ScannedCount,Items[].userId.S]' --output text
```
<Output>
```text
3	3
bo	ana	ana
```
</Output>
  </Run>
  <Verify>
    - Count and scanned count are both 3
    - The owners include `bo` and `ana`: one query now spans users
  </Verify>
</Lab>

<Lab title="never overwrite by accident" time="~2 min" collapsed>
  <Predict>
    `put-item` for a key that already exists, with the condition `attribute_not_exists(taskId)`. What happens?

    <Answer>
      It fails with `ConditionalCheckFailedException` and changes nothing. Without the condition, `put-item` silently replaces the old item.
    </Answer>
  </Predict>
  <Run>
```sh
aws dynamodb put-item --table-name tasks \
  --item '{"userId":{"S":"ana"},"taskId":{"S":"t1"},"title":{"S":"duplicate"}}' \
  --condition-expression 'attribute_not_exists(taskId)'
```
<Output>
```text
aws: [ERROR]: An error occurred (ConditionalCheckFailedException) when calling the PutItem operation: The conditional request failed
```
</Output>
  </Run>
  <Verify>
    - The call fails, and `get-item` for `ana` / `t1` still shows `task 1`
  </Verify>
</Lab>

## What changes on real AWS

<RealAws cost title="Indexes cost storage and writes">
  Every global secondary index stores its own copy of the data and consumes its own write capacity, so each index you add makes every write dearer. Add one per question you really ask. On real AWS an index also takes time to backfill on a large table, while LocalStack is ready in moments.
</RealAws>

<RealAws title="Hot partitions">
  A partition key chosen badly, such as a status with three values, sends most traffic to a few partitions, which throttle while the rest of the table sits idle. Choose a key with many distinct values and an even spread. Here `status` is fine for a lesson and poor for a busy table.
</RealAws>

<Note title="Design from the queries">
  Write down the questions first ("a user's tasks", "open tasks"), then pick the keys that answer them. Reshaping keys later means copying the table.
</Note>

<Recap>

- A query goes straight to one partition and needs the partition key; a scan reads the whole table and filters afterwards.
- The sort key orders items within a partition; the pair is the unique primary key.
- A global secondary index answers a different question under another key, at the price of extra storage and writes.

</Recap>
