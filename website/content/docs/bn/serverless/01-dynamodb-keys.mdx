## একটি প্রশ্ন, দ্রুত উত্তর

DynamoDB এমন ডেটাবেস নয় যেখানে পরে ফিল্টার করা হয়। প্রতিটি item থাকে তার **partition key** ঠিক করা জায়গায়: key-টি hash হয়, আর hash ঠিক করে কোন storage partition item-টি রাখবে। যে অনুরোধ key-র নাম বলে, সে সরাসরি সেখানে যায়। যে বলে না, তাকে সবগুলোয় ঘুরতে হয়।

- **Partition key**: আবশ্যক, partition বেছে নেয়। নিচের টেবিলে `userId`।
- **Sort key**: ঐচ্ছিক। একই partition key-র item-গুলো একসঙ্গে, sort key অনুযায়ী সাজানো থাকে, তাই তাদের একটি পরিসর আনা যায়। নিচে `taskId`।
- দুটি মিলে item-এর **primary key**, আর তা অনন্য হতে হবে।

অনেক item পড়ার দুটি operation, আর তারা একেবারে আলাদা:

| Operation | কী লাগে | কী পড়ে |
| --- | --- | --- |
| **Query** | partition key, আর ঐচ্ছিকভাবে sort key-র শর্ত | শুধু সেই key-র নিচের item |
| **Scan** | কিছুই না | টেবিলের প্রতিটি item, *তারপর* তোমার ফিল্টার চালায় |

Scan-এ ফিল্টার দিলে খরচ কমে না: যা ফেলে দিচ্ছ তা পড়ার দামও দিতে হয়। রিলেশনাল বা document ডেটাবেস থেকে এটাই চিন্তার বদল: আগে query ঠিক করো, তারপর এমন key বাছো যা সেগুলোকে দ্রুত করে। এখানে join নেই, ad-hoc query-ও নেই।

<Note title="বিল হয় প্রতি read ও write-এ">
  On-demand টেবিল প্রতি request unit-এ চার্জ করে, আর provisioned টেবিল প্রতি সেকেন্ডে throughput (RCU ও WCU) বিক্রি করে। দুই ক্ষেত্রেই খরচ নির্ভর করে তুমি কয়টি item ছুঁলে তার ওপর। LocalStack এটি নির্ভুলভাবে মাপে না, তাই নিচের ল্যাব তুলনা করে **কয়টি item পড়া হলো**, যার সঙ্গে বিল চলে।
</Note>

## বাস্তবে key

<Lab title="key দিয়ে query, scan, আর ভুল প্রশ্ন" time="~৬ মিনিট">
  <Predict>
    একটি টেবিলে `ana`-র তিনটি task (দুটি open, একটি done) আর `bo`-র একটি। তুমি `status = open` ফিল্টারসহ scan করলে। Response কয়টি item *ফেরত* দেবে, আর DynamoDB কয়টি *scan* করেছে?

    <Answer>
      ফেরত দেবে **৩**টি (open-গুলো), কিন্তু scan করেছে **৪**টি, মানে প্রতিটি item। ফিল্টার চলে পড়ার পরে। `userId = ana`-র query scan করত শুধু তার ৩টি।
    </Answer>
  </Predict>
  <Run>
```sh
export AWS_PROFILE=localstack

aws dynamodb create-table --table-name tasks \
  --attribute-definitions AttributeName=userId,AttributeType=S AttributeName=taskId,AttributeType=S \
  --key-schema AttributeName=userId,KeyType=HASH AttributeName=taskId,KeyType=RANGE \
  --billing-mode PAY_PER_REQUEST

aws dynamodb put-item --table-name tasks --item '{"userId":{"S":"ana"},"taskId":{"S":"t1"},"title":{"S":"task 1"},"status":{"S":"open"}}'
aws dynamodb put-item --table-name tasks --item '{"userId":{"S":"ana"},"taskId":{"S":"t2"},"title":{"S":"task 2"},"status":{"S":"done"}}'
aws dynamodb put-item --table-name tasks --item '{"userId":{"S":"ana"},"taskId":{"S":"t3"},"title":{"S":"task 3"},"status":{"S":"open"}}'
aws dynamodb put-item --table-name tasks --item '{"userId":{"S":"bo"},"taskId":{"S":"t1"},"title":{"S":"bo task"},"status":{"S":"open"}}'
```

আগে থেকে শুধু key attribute ঘোষণা করতে হয়; বাকি সব attribute (`title`, `status`) প্রতিটি item-এ মুক্ত। এবার key দিয়ে ana-র task চাও, তারপর একই টেবিলকে এমন প্রশ্ন করো যার উত্তর key দিতে পারে না:

```sh
echo "query by key:"
aws dynamodb query --table-name tasks --key-condition-expression 'userId = :u' \
  --expression-attribute-values '{":u":{"S":"ana"}}' \
  --query '[Count,ScannedCount]' --output text

echo "scan with a filter:"
aws dynamodb scan --table-name tasks --filter-expression '#s = :o' \
  --expression-attribute-names '{"#s":"status"}' \
  --expression-attribute-values '{":o":{"S":"open"}}' \
  --query '[Count,ScannedCount]' --output text

echo "query on a non-key attribute:"
aws dynamodb query --table-name tasks --key-condition-expression '#s = :o' \
  --expression-attribute-names '{"#s":"status"}' \
  --expression-attribute-values '{":o":{"S":"open"}}'
```
<Output>
```text
query by key:
3	3
scan with a filter:
3	4
query on a non-key attribute:

aws: [ERROR]: An error occurred (ValidationException) when calling the Query operation: Query condition missed key schema element: userId
```
</Output>
  </Run>
  <Verify>
    - Query ৩ ফেরত দেয় আর scan করে ৩: শুধু ana-র item ছুঁয়েছে
    - Scan ৩ ফেরত দেয় কিন্তু scan করে ৪: বাদ দেওয়ার জন্যই bo-র item-ও পড়েছে
    - তৃতীয় কমান্ডটি **প্রত্যাখ্যাত**: query-তে partition key-র নাম বলতেই হয়
  </Verify>
</Lab>

## দ্বিতীয় প্রশ্নের জন্য দ্বিতীয় key

"সব open task, মালিক যেই হোক" একটি ভিন্ন প্রশ্ন, আর `status` primary key-তে নেই। উত্তর হলো **global secondary index** (GSI): টেবিলের একটি কপি, যা তোমার জন্য আপডেট থাকে, আর সাজানো অন্য key-র নিচে। Index-কে query করো ঠিক টেবিলের মতোই।

<Lab title="index যোগ করে আবার জিজ্ঞেস করো" time="~৪ মিনিট">
  <Predict>
    তুমি partition key `status` দিয়ে একটি index যোগ করলে, আর `status = open` দিয়ে query করলে। কয়টি item scan হবে, আর সেগুলো এক ইউজারের না একাধিকের?

    <Answer>
      **৩টি scan, ৩টি ফেরত**, দুই ইউজারেরই: index সাজানো status অনুযায়ী, তাই open item-গুলো মালিক নির্বিশেষে একসঙ্গে থাকে।
    </Answer>
  </Predict>
  <Run>
```sh
aws dynamodb update-table --table-name tasks \
  --attribute-definitions AttributeName=status,AttributeType=S AttributeName=taskId,AttributeType=S \
  --global-secondary-index-updates '[{"Create":{"IndexName":"by-status",
    "KeySchema":[{"AttributeName":"status","KeyType":"HASH"},{"AttributeName":"taskId","KeyType":"RANGE"}],
    "Projection":{"ProjectionType":"ALL"}}}]'
sleep 3

aws dynamodb query --table-name tasks --index-name by-status \
  --key-condition-expression '#s = :o' \
  --expression-attribute-names '{"#s":"status"}' \
  --expression-attribute-values '{":o":{"S":"open"}}' \
  --query '[Count,ScannedCount,Items[].userId.S]' --output text
```
<Output>
```text
3	3
bo	ana	ana
```
</Output>
  </Run>
  <Verify>
    - Count আর scanned count দুটোই ৩
    - মালিকদের মধ্যে `bo` ও `ana` দুজনেই: একটি query এখন ইউজার পেরিয়ে যায়
  </Verify>
</Lab>

<Lab title="ভুলে overwrite হতে দিয়ো না" time="~২ মিনিট" collapsed>
  <Predict>
    যে key আগে থেকেই আছে তার জন্য `put-item`, শর্ত `attribute_not_exists(taskId)` দিয়ে। কী হবে?

    <Answer>
      এটি `ConditionalCheckFailedException` দিয়ে ব্যর্থ হয় আর কিছুই বদলায় না। শর্ত না দিলে `put-item` চুপচাপ পুরোনো item বদলে দেয়।
    </Answer>
  </Predict>
  <Run>
```sh
aws dynamodb put-item --table-name tasks \
  --item '{"userId":{"S":"ana"},"taskId":{"S":"t1"},"title":{"S":"duplicate"}}' \
  --condition-expression 'attribute_not_exists(taskId)'
```
<Output>
```text
aws: [ERROR]: An error occurred (ConditionalCheckFailedException) when calling the PutItem operation: The conditional request failed
```
</Output>
  </Run>
  <Verify>
    - কলটি ব্যর্থ হয়, আর `ana` / `t1`-এর `get-item` এখনো `task 1` দেখায়
  </Verify>
</Lab>

## রিয়েল AWS-এ যা বদলায়

<RealAws cost title="Index-এর খরচ storage আর write-এ">
  প্রতিটি global secondary index নিজের ডেটার কপি রাখে আর নিজের write capacity খায়, তাই প্রতিটি index প্রতিটি write-কে আরও দামি করে। যতগুলো প্রশ্ন সত্যিই করো, ততগুলোই index যোগ করো। রিয়েল AWS-এ বড় টেবিলে index backfill হতেও সময় লাগে, আর LocalStack কয়েক মুহূর্তেই তৈরি।
</RealAws>

<RealAws title="Hot partition">
  খারাপভাবে বাছা partition key, যেমন তিন মানের একটি status, বেশিরভাগ ট্রাফিক কয়েকটি partition-এ পাঠায়, যেগুলো throttle হয় আর টেবিলের বাকিটা অলস পড়ে থাকে। অনেক ভিন্ন মান আর সমান বণ্টনের key বাছো। এখানে `status` পাঠের জন্য ঠিক, ব্যস্ত টেবিলের জন্য নয়।
</RealAws>

<Note title="Query থেকে ডিজাইন করো">
  আগে প্রশ্নগুলো লেখো ("একজন ইউজারের task", "open task"), তারপর সেগুলোর উত্তর দেয় এমন key বাছো। পরে key বদলানো মানে টেবিল কপি করা।
</Note>

<Recap>

- Query সরাসরি একটি partition-এ যায় আর partition key লাগে; scan পুরো টেবিল পড়ে, ফিল্টার করে পরে।
- Sort key partition-এর ভেতরে item সাজায়; জোড়াটি অনন্য primary key।
- Global secondary index অন্য key-র নিচে ভিন্ন প্রশ্নের উত্তর দেয়, বাড়তি storage ও write-এর দামে।

</Recap>
